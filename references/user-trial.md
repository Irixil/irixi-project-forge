# DZ beginner trial

Use real project feedback to assess whether DZ saves the beginner effort. This is a trial of DZ, not a requirement for a product owner to personally run production acceptance tests. Do not manufacture a trial, interrupt ordinary delivery with a survey, or treat the owner's promised future feedback as a passed test.

When relevant in a real project, observe:

- The user starts with an unclear idea or says “I don't know”: does DZ recommend one understandable next step without silently choosing an important promise?
- The user corrects direction: does affected work stop, compatible work stay, and the agreed correction govern the next action?
- Someone changes files after the saved record: does a new conversation find the present position, discuss the route, and avoid overwriting the later work?
- Work moves to another host: does it load current records and honestly state unavailable capabilities, rather than claiming memory or execution it lacks?

Record only observed failures and decision-changing feedback in the existing issue/feedback records: the user's words or permitted reference, expected/actual behavior, omitted requirements, unnecessary repeated questions, discarded compatible work, avoidable work/time, and the smallest correction worth testing. Keep private transcripts out of public reports.

One failure is actionable evidence, not a universal score. Mark each untried situation and host **not tested**. Check usefulness and understanding separately from correctness of the ledger. Avoid numerical ratings, targets, or comparison claims without an agreed method and actual observations.
