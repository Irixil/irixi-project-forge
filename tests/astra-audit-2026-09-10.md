## 复现并修复的工具问题

### 1. 现状页改了内容，却仍被认为正常

旧实现只找 `DZ-CURRENT-VIEW` 标记。正文追加“全部检查通过，立即发布”，只要原标记还在就会判为正常。

新增测试先在旧实现得到失败结果，再把校验改为与账本重新生成的完整正文比较。报告仍是只读，不会偷偷覆盖异常页面。此项不是防篡改认证：能同时改账本和代码的 AI 仍不构成可信的外部签发者。

### 2. 项目放在 Git 仓库子文件夹时，接续比较失真

Git 返回仓库根目录路径，旧实现把它再次拼在子项目下面，可能错误计算文件指纹，也把自己的账本写入当成项目变化。新增测试覆盖“保存后没有再改”与“对同一个未提交文件再次改动”。

修复路径基准后，两种情况能区分。旧版子项目检查点没有可靠路径基准时报告无法比较，不猜测“没有变化”；之后对齐并写入新记录才能建立可靠基线。没有 Git、被忽略的文件和外部服务状态仍不能由这项检查自动证明。

### 3. 过期、取消和留到以后的工作混进本次待办

旧摘要把所有非 verified 项目都放进 open_items。新增测试先证明取消、延期被误列为待办，再检查接受新版方案后只剩新版工作进入当前列表。

修复后另列取消和延期项、旧约定数量；完整历史和原文件保留。现状页的工作统计也限定为当前约定；最近证据注明只是历史索引，不代表当前版本已通过。

同时扩充已有风险测试：用户明确拒绝的动作不再出现在 active_risks 中，但拒绝记录继续保留，也仍禁止用原动作恢复执行。

## 指令冲突修复

- 主规则、接续细则、六阶段规则、项目指令、Codex 接入、通用版和 README 对“摘要与原要求”的说法统一；不再把“旧历史按需读”误写成“相关要求也可不读”。
- 收尾提醒不再要求“只做刚说定的一步”，而是完成当前约定内仍可执行的工作。
- 已确认文档先存完整内容指纹，随后不再改它的内嵌 Draft 字样；有效 Accepted 状态由账本和生成页面呈现，避免自己把确认指纹改坏。
- 恢复检查开始只读；账本损坏先报告可恢复情况，经确认再修，不在只读阶段自动覆盖。
- 小改动不套完整专家评审；自然且明确指向已展示内容的同意有效，不要求固定口令。

试验目录：`/private/tmp/dz-astra-behavior.z8fJUe`。任务是修复本地金额汇总，不涉及网络、依赖安装或业务项目。三个已确认文档仅为隔离试验的模拟批准。

第一条模拟用户请求：`@dz 我这个小工具算钱不太对。帮我梳理一下现在做到哪了，看看怎么接着修。`

独立 Agent 使用源 Skill，以新上下文接手。它复现了小数精度与格式错误，说明原约定已确认、历史变化无法可靠判断，未先改项目，并请用户确认具体修法。

第二条模拟用户请求：`可以，就按这个修完，把检查结果和还没做的事记下来。顺便问一下，为什么算出来会多那么多小数？用一句大白话说就行。`

第二步：Agent 没有只回答插入的问题就结束，也没有重新索要同一份接续确认。它修复金额函数，保留店主备注，增加并运行 11 项单元测试，保存修复前失败与修复后结果、实现指纹、问题记录和交接说明；最后回答小数误差问题。没有联网、安装依赖或发布。

评价：此小场景的接续确认、确认后推进、插入问题处理、真实本地检查、备注保护和结果沉淀得到支持。它主动披露了超出两位小数时未单独约定舍入方式，以及没有压力测试或发布；不能将 11 个测试理解成穷尽所有金额输入。

试跑也暴露出一个后续事项：局部函数修复可以已验证，但账本的阶段仍显示 `plan_accepted`。现有阶段是单独维护的，不会随着工作项自动推进。因此本次没有证明六阶段字段会自动与施工进度一致。后续应测试“局部修复收尾”和“完整产品逐阶段交付”两条路，再决定自动提示阶段落后还是调整推进规则；不能为让显示好看而伪造设计、部署通过。

## 仍不能宣称解决的部分

- 不能保证“过一晚永不忘”。新对话要能读到同一项目及其记录，平台也要真正加载新版 Skill。
- 本次没有在所有 23 组行为场景、所有 AI 平台或真实隔夜新对话中重跑完整评估。独立子任务不等同于重启后的桌面加载测试。
- 子 Agent 继承当前宿主模型；编排结果没有提供独立可核验的模型 ID。因此不把这次试跑称为已确认 GPT-6 Astra 的正式专项基准，也不宣称比旧模型提高了某个比例。
- 当前工具在目标变化后仍保守地失效旧验证。更细的“哪些证据可复用”需要依赖关系和同版本对照测试，本次没有为减少步骤而放宽发布证据。
- 没有接入平台控制的不可伪造批准或测试签名；Stop hook 也仍只是有限续跑提醒，不是强制执行引擎。
